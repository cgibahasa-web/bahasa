# 2027 CGI BAHASA 웹사이트 제작 세부계획

작성일: 2026-09-19  
목표: VS Code와 AI 코딩 도구를 이용해 인도네시아어 중심의 행사 안내 웹사이트를 7일 안에 공개하고, 같은 코드 기반에 등록·현지 결제·운영 기능을 단계적으로 추가한다.

## 1. 이번 계획의 전제

이 문서는 행사 및 운영상의 쟁점이 모두 해결된다는 전제로 작성한다. 다음 정보를 공식 확정값으로 받아 사이트 구조를 설계한다.

- 행사명: 2027 CGI BAHASA Conference
- 일정: 2027년 10월 11일~14일, 3박 4일
- 장소: 오산리최자실기념금식기도원
- 주최: CGI
- 예상 참가자: 약 1,000명
- 기본 언어: 인도네시아어(ID), 보조 언어: 영어(EN)
- 운영 언어: 관리자 화면과 내부 문서는 한국어(KO)
- 1차 목표: 공식 안내 웹사이트 공개
- 2차 목표: 개인·단체 등록, 인도네시아 현지 결제, 등록 확인, 운영자 관리

일정·등록비·환불 규정·도메인·공식 이메일·결제 계약 등은 준비 과정에서 확정된 값으로 교체하며, 구조를 다시 만들지 않고 데이터만 바꿀 수 있게 한다.

## 3. 권장 기술 구성

| 영역 | 권장 선택 | 선택 이유 |
|---|---|---|
| 개발 환경 | VS Code + Git + GitHub | AI 작업 이력과 사람의 승인 이력을 함께 남기기 쉽다 |
| 웹 프레임워크 | Next.js + TypeScript | 안내 페이지와 추후 서버 API·관리자·결제를 한 프로젝트에서 확장할 수 있다 |
| 스타일 | Tailwind CSS + 공통 디자인 토큰 | 모바일 대응과 색상·간격·버튼 규칙을 일관되게 유지한다 |
| 다국어 | `next-intl`, `/id`와 `/en` 주소 | 언어별 검색 노출과 번역 누락 검사가 쉽다 |
| 콘텐츠 | 1차는 코드 내 구조화 데이터/MDX | 별도 CMS 없이 빠르고 안정적으로 공개한다 |
| 데이터베이스 | 2차부터 Supabase PostgreSQL | 등록·결제·운영 데이터를 관계형으로 관리하기 좋다 |
| 파일 저장 | Supabase Storage 또는 S3 계열 | 초청장용 서류를 공개 이미지와 분리하고 접근을 제한한다 |
| 이메일 | Resend 또는 동급 서비스 | 접수·결제·취소 안내를 서버에서 기록하며 발송한다 |
| 현지 결제 | Midtrans 개인 계정 + Payment Link | 법인 서류와 자체 결제 화면 없이 Midtrans의 결제 페이지에서 QRIS·은행 Virtual Account·GoPay를 제공한다 |
| 배포 | Vercel | Next.js 배포·미리보기·도메인 연결이 단순하다 |
| 테스트 | Vitest + Testing Library + Playwright | 함수·화면·실제 사용자 흐름을 단계별로 검증한다 |
| 모니터링 | Vercel 로그 + 오류 추적 도구 | 공개 후 흰 화면, 서버 오류, 결제 통지 실패를 찾는다 |

1차 사이트에는 데이터베이스와 관리자 화면을 억지로 넣지 않는다. 행사 내용은 한 곳의 구조화된 파일에서 관리하고, 같은 날짜·금액·장소가 여러 화면에 중복 입력되지 않게 한다.

## 4. 사이트 구조

```text
/id                         인도네시아어 홈
/en                         영어 홈
├── /about                  행사 취지, 주최, 대상, 인사말
├── /program                날짜별 전체 일정, 세미나, 집회, 선택 프로그램
├── /venue                  기도원, 숙소, 오시는 길, 현장 시설
├── /participant-guide      참가비, 포함 항목, 준비물, 식사, 교통
├── /travel-visa            해외 참가자 여행·초청장 안내
├── /registration           등록 상태, 후속 등록 폼 진입점
├── /faq                    자주 묻는 질문
├── /contact                공식 문의
├── /privacy                개인정보처리방침
└── /terms                  이용약관 및 환불 규정
```

홈 화면은 다음 순서로 구성한다.

1. 행사명, 주제, 날짜, 장소, 주 행동 버튼
2. 행사 목적과 참가 대상
3. 핵심 프로그램과 날짜별 일정 미리보기
4. 실제 기도원·예배 현장 사진
5. 참가비와 포함 항목 요약
6. 해외 참가자 준비 안내
7. FAQ
8. 등록 또는 문의 버튼

첫 화면은 실제 기도원 또는 예배 사진을 크게 사용한다. 포스터는 보조 홍보물로 활용하며, 페이지의 주요 정보를 포스터 이미지 안에만 넣지 않는다.

## 5. 디자인 기준

- 전체 분위기: 신뢰감 있는 국제 기독교 행사, 따뜻하고 선명한 현장성
- 주 색상: 네이비, 골드, 아이보리를 기본으로 하되 흰색·빨강 포인트를 함께 사용
- 본문: 밝은 배경, 충분한 글자 크기, 짧은 문단
- 모바일 우선: 360px 너비에서도 메뉴·표·버튼·긴 인도네시아어 문장이 잘리지 않아야 한다
- 버튼: `Daftar`, `Lihat Program`, `Hubungi Kami`처럼 행동이 분명한 문구 사용
- 일정: 복잡한 표보다 날짜별 탭 또는 세로 목록 사용
- 접근성: 키보드 이동, 색상 대비, 이미지 대체문구, 폼 오류 안내 적용
- 사진: 사용 권한과 출처를 기록하고, 원본을 웹용 크기로 최적화

## 6. 7일 제작 범위

7일 안에 공개하는 버전은 정보 제공에 집중한 `v1 안내 사이트`다. 다음 항목을 공개 필수 범위로 고정한다.

- ID/EN 언어 전환
- 홈, 행사 소개, 프로그램, 장소, 참가 안내
- 여행·비자 핵심 안내
- FAQ와 이메일·WhatsApp 문의 연결
- 개인정보처리방침과 이용약관
- 등록 페이지의 `등록 준비 중` 상태
- 모바일·PC 반응형 화면
- 검색·공유 기본정보, 사이트맵, 404 화면
- Vercel 운영 배포, 공식 도메인, HTTPS

일주일 동안 다음 기능은 만들지 않는다.

- 회원가입과 로그인
- 데이터베이스와 관리자 화면
- 개인·단체 등록 폼
- 실제 결제와 환불
- 여권·초청장 파일 업로드
- 범용 CMS
- 라이브 방송, 갤러리, 현장 체크인
- 복잡한 문의 폼과 자동 이메일

문의는 공식 이메일과 WhatsApp 링크로 연결한다. 결제 버튼은 열지 않고 `Pendaftaran segera dibuka`와 문의처를 표시한다.

### 7.1 7일 일정의 운영 규칙

- 매일 한 번 미리보기 주소를 공유하고, 당일 승인 항목은 같은 날 확정한다.
- 수정 요청은 한 명의 최종 승인자가 모아서 전달한다.
- 4일차 이후에는 페이지 추가나 디자인 방향 변경을 받지 않는다.
- 5일차부터는 오류, 사실관계, 번역, 모바일 표시 문제만 수정한다.
- ID 번역이 늦어지면 승인된 한국어·영어 원문을 AI로 번역해 넣고, 6일차에 현지 감수자가 교정한다.
- 도메인 연결이 늦어져도 Vercel 운영 주소로 먼저 공개하고, 도메인은 준비되는 즉시 연결한다.
- 치명적 오류가 발견되면 해당 부분만 숨기고 나머지 사이트를 예정대로 공개한다.

### 7.2 7일차 공개 기준

- ID/EN 홈과 핵심 페이지가 모두 열림
- 행사명·일정·장소·주최·연락처가 모든 화면에서 일치함
- 360px 모바일과 일반 PC 화면에서 겹침·가로 스크롤이 없음
- 모든 메뉴·언어 전환·문의 링크가 작동함
- 임시 문구, 빈 이미지, 개발용 데이터가 없음
- 개인정보처리방침과 이용약관이 연결됨
- 등록·결제가 아직 열리지 않았다는 안내가 분명함
- 운영 배포와 이전 버전 복구 방법이 확인됨

등록·결제 시스템은 사이트 공개 후 별도 2차 일정으로 시작한다. Midtrans 시험환경, 등록 데이터, 관리자 화면, 결제 결과 검증, 취소·환불은 공개 사이트의 안정성을 해치지 않는 별도 기능으로 추가한다.

## 8. 향후 등록·결제 구조

### 8.1 결제수단 우선순위

| 우선순위 | 결제수단 | 적용 방식 |
|---|---|---|
| 1 | QRIS 동적 결제 | 주문별 금액과 만료시간이 포함된 QR을 생성하고, 모바일뱅킹·GoPay·DANA·OVO·ShopeePay 등 QRIS 지원 앱에서 결제 |
| 2 | GoPay 직접 결제 | 모바일에서 GoPay 앱으로 이동해 승인할 수 있는 간단한 흐름 제공 |
| 3 | 은행 Virtual Account | Permata, BNI, BRI, Mandiri 등 활성화된 은행의 주문별 가상계좌 제공 |
| 4 | 국제 신용·체크카드 | 인도네시아 계정이나 QRIS를 사용할 수 없는 참가자의 보조 수단 |

PayPal은 주 결제수단으로 사용하지 않는다. 인도네시아 참가자에게는 QRIS와 IDR 가격을 먼저 보여주고, QRIS 사용이 어려운 경우 GoPay·은행·카드를 선택하게 한다. DANA·OVO·ShopeePay는 초기에는 별도 직접 연동하지 않고 QRIS 지원 앱으로 사용한다.

현지 가격은 실시간 환율로 매 결제마다 바꾸지 않고, 재정 담당자가 승인한 고정 IDR 금액을 등록 기간별로 게시한다. 주문에는 적용된 가격표 버전, IDR 금액, 할인, 결제수단을 함께 저장한다.

### 8.2 가장 간단한 초기 방식

결제사는 Midtrans만 사용하고, Midtrans의 호스팅 결제 페이지인 Payment Link로 연결한다. 자체 결제수단 선택 화면이나 카드 입력 화면은 만들지 않는다.

```text
웹사이트 등록 완료
    -> 등록번호와 고정 IDR 금액 생성
    -> 등록별 Midtrans Payment Link 생성
    -> Midtrans 결제 페이지로 이동
    -> 참가자가 QRIS·GoPay·은행 가상계좌 선택
    -> 결제 결과 통지
    -> 웹사이트에서 결제 완료 표시
```

- 가맹점 유형은 인도네시아 국내 `Individu`로 신청한다.
- 법인·재단의 정관, 설립증서, 사업허가 서류는 초기 방식에서 요구하지 않는다.
- 대신 현지 명의자의 KTP, NPWP, 같은 이름의 인도네시아 은행계좌가 필요하다.
- 운영자가 BCA·BRI·BNI·Mandiri에 직접 계좌를 개설하는 것이 아니다. 승인된 Midtrans 가맹점 계정이 주문마다 결제용 Virtual Account 번호를 생성한다.
- 운영자는 한국에서도 Midtrans 대시보드와 웹사이트를 통해 Virtual Account를 생성·조회할 수 있다.
- 현지 개인 계정 승인이 완료되지 않은 동안에는 Sandbox의 가상 Virtual Account만 생성할 수 있고 실제 입금은 받을 수 없다.
- 공개된 웹사이트에 행사명과 IDR 등록비가 보여야 한다.
- 등록별 결제 링크를 사용해 입금자와 참가자를 자동으로 연결한다.
- 초기에는 Midtrans가 제공하는 화면을 그대로 사용해 결제 UI 개발과 보안 범위를 줄인다.
- 현지 개인 명의자와 KTP·NPWP도 준비할 수 없는 동안에는 실제 온라인 결제를 열지 않고, 시험환경에서만 개발한다.

Xendit은 개인 사업자 계정을 받지 않으므로 초기 후보에서 제외한다. 법인 또는 정식 사업체가 준비된 뒤에만 재검토한다.

### 8.3 결제 처리 흐름

```text
참가자 브라우저
    |
    | 등록 정보 제출
    v
Next.js 서버 ──검증──> PostgreSQL 등록 레코드
    |                         |
    | 결제 생성               | 상태 조회
    v                         v
인도네시아 결제사 <──통지── 결제 처리 서비스
    |                         |
    | 성공/실패               | 검증 후 상태 변경
    v                         v
참가자 안내 화면          이메일 + 관리자 화면
```

등록과 결제는 다음 상태를 분리한다.

```text
DRAFT -> SUBMITTED -> PAYMENT_PENDING -> PAID
                       |                 |
                       v                 v
                  PAYMENT_FAILED     CANCEL_REQUESTED
                                         |
                                         v
                                  REFUND_PENDING -> REFUNDED
```

- 브라우저의 결제 완료 화면만으로 `PAID` 처리하지 않는다.
- 결제사의 서버 통지를 서명 검증한 뒤 상태를 변경한다.
- 같은 통지가 반복되어도 한 번만 처리되도록 고유 결제번호를 사용한다.
- 금액·통화·결제사 거래번호·환불 금액을 별도 기록한다.
- QRIS와 Virtual Account에는 만료시간을 표시하고, 만료 후 입금과 지연 통지를 별도 처리한다.
- QRIS 환불 가능 범위가 발급 앱마다 다를 수 있으므로 자동 환불 실패 시 재정 담당자의 수동 계좌 환불과 처리 기록을 지원한다.
- 일반 등록에는 여권 사본을 받지 않는다. 초청장 신청에서만 별도 동의와 제한된 권한으로 수집한다.

## 9. 테스트 계획

```text
안내 사이트 사용자 흐름
[홈 진입]
  ├─ ID 기본 표시 ── 언어 전환 ── EN 동일 내용 확인
  ├─ 프로그램 선택 ── 날짜별 일정/빈 일정/긴 제목 확인
  ├─ 장소 선택 ── 사진/주소/지도 링크 확인
  ├─ 등록 선택 ── 준비 중 또는 실제 등록 상태 확인
  └─ 문의 제출
       ├─ 정상 입력 -> 성공 안내 + 관리자 수신
       ├─ 잘못된 입력 -> 해당 필드 오류 안내
       ├─ 중복 클릭 -> 한 번만 전송
       └─ 서버 실패 -> 재시도 가능한 오류 안내

등록·결제 후속 흐름 [E2E 필수]
[등록 제출] -> [결제 생성] -> [결제사] -> [서버 통지] -> [PAID] -> [이메일]
   ├─ 유효성 오류
   ├─ 결제 포기/실패
   ├─ 느린 통지
   ├─ 중복 통지
   ├─ 금액 불일치
   ├─ 마감 직전 동시 신청
   └─ 취소/부분 환불/전체 환불
```

### 9.1 결제 테스트 순서

#### 1단계. Midtrans Sandbox

- 실제 한국카드를 사용하지 않고 Midtrans가 제공하는 시험용 카드번호와 OTP를 사용한다.
- 성공, 카드 거절, 인증 실패, 처리 지연, 사용자의 결제 중단을 각각 시험한다.
- QRIS·GoPay·Virtual Account는 Midtrans 시뮬레이터로 상태 변경을 시험한다.
- 화면의 성공 표시가 아니라 서버 통지와 Midtrans 거래 조회 결과로 `PAID` 상태가 되는지 확인한다.

Sandbox 예시 성공 카드: Visa `4811 1111 1111 1114`, CVV `123`, 미래 만료일, 시험 OTP `112233`. 이 정보는 Sandbox에서만 사용하며 운영환경에서는 작동하지 않는다.

#### 2단계. 한국 발급 카드 운영환경 소액 결제

- Midtrans 운영 계정과 카드 결제 채널이 승인된 뒤 진행한다.
- 해외 온라인 결제와 3D Secure 인증이 가능한 한국 발급 Visa 또는 Mastercard를 사용한다.
- 결제 요청 금액은 IDR로 표시하고, 카드사는 이를 원화로 환산할 수 있으며 해외 이용 수수료가 발생할 수 있음을 안내한다.
- 허용되는 최소 수준의 실제 금액으로 결제하고, Midtrans 대시보드·웹사이트 상태·결제 완료 안내를 함께 대조한다.
- 시험 후 실제 환불을 실행해 환불 상태와 정산 기록까지 확인한다.
- 실제 카드번호·유효기간·CVV는 Midtrans 결제 페이지에만 입력하며 웹사이트, 문서, AI 대화, 로그에 남기지 않는다.

#### 3단계. 인도네시아 현지 결제

- 현지 사용자의 모바일뱅킹 또는 DANA·OVO·ShopeePay 등 QRIS 지원 앱으로 QRIS를 결제한다.
- GoPay 앱 직접 이동과 결제 후 복귀를 모바일에서 확인한다.
- 가능하면 활성화된 은행 Virtual Account로 입금과 만료도 확인한다.
- 한국 은행의 일반 해외송금은 실시간 도착과 만료시간을 보장하기 어려우므로 Virtual Account 운영 테스트의 기본 방법으로 사용하지 않는다.
- 한국 운영자는 한국카드로 카드 경로를 시험하고, 인도네시아 현지 사용자가 현지 은행계좌로 Virtual Account 경로를 시험한다.
- 성공뿐 아니라 결제 취소, QR 만료, 늦은 입금, 중복 버튼, 환불 안내를 확인한다.
- 현지 사용자가 이해하기 어려운 용어와 단계가 없는지 화면 녹화 또는 관찰 기록으로 검수한다.

한국카드 운영 테스트는 카드 결제 경로를 검증하고, 현지 테스트는 실제 주 사용 경로인 QRIS·GoPay·Virtual Account를 검증한다. 두 시험을 모두 통과해야 결제를 공개한다.

| 실패 가능성 | 예방·처리 | 검증 방식 | 사용자에게 보이는 결과 |
|---|---|---|---|
| 번역 키 누락 | 빌드 시 누락 검사 | 자동 테스트 | 기본 언어로 조용히 섞이지 않고 배포가 중단됨 |
| 일정 변경 후 일부 화면만 갱신 | 단일 데이터 원본 | 단위·화면 테스트 | 모든 화면에 같은 일정 표시 |
| 모바일에서 긴 문장 잘림 | 반응형 규칙과 실제 기기 폭 검사 | Playwright 스크린샷 | 줄바꿈되어 전체 문구 표시 |
| 문의 폼 중복 전송 | 제출 중 버튼 잠금과 서버 중복 방지 | 통합 테스트 | 한 번만 접수되고 결과 안내 |
| 이미지로 페이지가 느려짐 | 크기 변환·지연 로딩·용량 제한 | Lighthouse | 핵심 정보가 먼저 표시 |
| 결제 통지 중복 | 고유키와 트랜잭션 처리 | E2E·통합 테스트 | 중복 등록·중복 이메일 없음 |
| 결제사는 성공, 서버는 지연 | 재조회와 재처리 작업 | 장애 시나리오 테스트 | 처리 중 안내 후 최종 상태 복구 |
| QRIS·가상계좌가 만료된 뒤 입금 | 만료 상태와 지연 입금 대조 | E2E·정산 테스트 | 자동 확정하지 않고 확인 필요 안내 |
| 자동 환불이 지원되지 않는 채널 | 수동 환불 절차와 증빙 기록 | 환불 통합 테스트 | 환불 진행 상태와 완료일 안내 |
| 개인정보 무단 접근 | 역할 기반 권한과 접근 기록 | 권한 테스트 | 권한 없는 운영자는 접근 불가 |

- 소개: 대회 취지, CGI 소개, 인사말, 대상 참가자

- 여행·비자: 초청장 대상, 제출 항목, 접수 기간, 처리 담당, 주의 문구
- FAQ: 실제 문의가 많은 질문 10~20개와 승인 답변
- 문의: 수신 담당자, 답변 가능 언어, 목표 답변 시간
- 정책: 개인정보처리방침, 이용약관, 환불 규정, 사진·영상 촬영 동의

- Vercel 주최 측 계정


- 파일명에 `최종`, `진짜최종`을 반복하지 않고 날짜와 버전을 넣는다.
- 예: `program-id-v03-2026-10-02.docx`
- 수정 요청은 화면 캡처만 보내지 않고 페이지 주소, 문구, 변경 내용을 함께 기록한다.
- 승인된 원고는 승인자·승인일을 표기하고 읽기 전용으로 보관한다.

## 12. AI와 함께 개발하는 작업 규칙

1. 모든 AI 작업은 같은 요구사항 문서와 콘텐츠 원본을 기준으로 한다.
2. 한 작업의 목표, 수정 범위, 완료 기준을 먼저 적고 코드를 생성한다.
3. 한 AI가 구현하면 다른 AI 또는 별도 검토 단계에서 오류와 누락을 확인한다.
4. 실제 개인정보·비밀번호·결제 비밀키를 대화나 코드에 넣지 않는다.
5. 큰 변경 전에 Git에 정상 동작 상태를 남긴다.
6. AI의 완료 보고보다 브라우저 테스트 결과를 우선한다.
7. 디자인 변경은 모바일과 PC 화면을 함께 캡처해 승인한다.
8. 일정·금액·정책 변경은 코드부터 고치지 않고 콘텐츠 원본부터 수정한다.

## 13. 1차 공개에서 제외하는 범위

- 실제 등록과 결제: 안내 사이트 검수 후 2차 단계에서 구현
- 관리자 대시보드: 등록 데이터가 생기는 2차 단계에서 구현
- 여권 사본·초청장 파일 업로드: 보안·보관 체계와 함께 2차 단계에서 구현
- 현장 QR 체크인: 등록 운영 방식이 확정된 뒤 별도 판단
- 라이브 방송과 영상 보관: 방송 운영 담당과 저작권 기준 확정 후 추가
- 범용 CMS: 초기 콘텐츠 변경 빈도를 확인한 뒤 필요할 때 도입
- 모바일 앱: 웹사이트만으로 참가자 흐름을 충족하므로 제외
- 자체 카드 입력·결제수단 선택 화면: Midtrans Payment Link가 담당하므로 제외
- Xendit 및 복수 결제대행사 연동: 개인 가맹점 요건과 단순 운영 원칙에 맞지 않아 제외

## 14. 공개 승인 체크리스트

- [ ] ID/EN 모든 페이지에 임시 문구와 끊어진 링크가 없다
- [ ] 행사명·일정·장소·주최·연락처가 모든 화면에서 일치한다
- [ ] 모바일 360px에서 가로 스크롤과 글자 겹침이 없다
- [ ] 대표 사진과 로고의 사용 권한이 기록되어 있다
- [ ] 문의 성공·오류·중복 클릭이 모두 테스트됐다
- [ ] 개인정보처리방침·이용약관·환불 규정 링크가 보인다
- [ ] 도메인·HTTPS·공유 이미지·사이트맵이 정상이다
- [ ] 인도네시아 현지 검수자가 핵심 흐름을 완료했다
- [ ] 운영자가 콘텐츠 변경과 장애 연락 절차를 알고 있다
- [ ] 배포 이전 버전으로 되돌리는 절차가 준비되어 있다

## 15. 바로 착수할 순서

1. 기존 자료에서 공식 행사 정보와 사용할 이미지를 선별한다.
2. `website/` 폴더에 Next.js 프로젝트와 Git 저장소를 만든다.
3. 홈 화면의 모바일·PC 시안을 먼저 만든다.
4. 홈 시안 승인 후 공통 디자인과 전체 페이지를 확장한다.
5. ID 원고를 기준 언어로 넣고 EN 번역을 연결한다.
6. 자동 테스트와 실제 브라우저 검수를 통과시킨다.
7. 미리보기 주소에서 운영진·현지 검수 후 공식 도메인에 공개한다.

첫 제작 작업의 완료 산출물은 `실행 가능한 프로젝트`, `홈 화면 시안`, `콘텐츠 입력 구조`, `ID/EN 언어 전환`, `모바일 캡처` 다섯 가지로 한다.
